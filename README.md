## Первое правило

Перед первым использованием сделайте в текущем окружении:

```
pip install nbstripout
nbstripout --install
```

Это нужно, чтобы в гит не писался вывод в ipynb'ах. Иначе будут проблемы с конфликтами коммитов.

## Второе правило

Один человек --- один нотебук. За исключением финального, его нужно будет как-то делать особенно. Правило не жесткое но желательное.

## Третье правило

Работаем строго в своих в ветках под задачу.

Цикл такой:

```
git switch main
git pull
git switch -c feature/clean-data     # новая ветка под задачу

# работаете, коммитите
git add .
git commit -m "Очистка пропусков в sales.csv"
git push -u origin feature/clean-data
```

После пуша GitHub предложит кнопку `Compare & pull request`. Заполняете описание и выбираете ревьюера (Reviewers справа). Ревьюер оставляет комментарии или нажимает Approve. После одобрения вы жмёте Merge (удобнее всего `Squash and merge`: вся ветка превращается в один коммит) и удаляете ветку. Остальные потом делают `git switch main` && `git pull origin`

## Возможные конфликты

Допустим, Аня и Борис оба ответвились от main и изменили одно и то же место (например, один ноутбук). Первым вливают PR Ани, и в main появляются её изменения. Теперь у PR Бориса GitHub показывает: «This branch has conflicts that must be resolved», и кнопка Merge блокируется. Оба PR сами по себе нормальные, конфликт возникает только после слияния первого. Разрешает его автор второго PR, то есть Борис.

Как Борис разрешает конфликт

```
git switch feature/boris
git fetch origin
git merge origin/main          # git сообщит о конфликтах
# открываете файлы, правите маркеры <<<<<<< ======= >>>>>>>
git add <файлы>
git commit                     # завершает слияние
git push
```

### `git switch feature/boris`

Переключает вас на ветку feature/boris, то есть на ветку Бориса с его работой. Файлы в папке меняются на состояние этой ветки. Нужно, чтобы дальнейшие действия применялись именно к ней.

### `git fetch origin`

Скачивает с GitHub (origin) все новые коммиты и обновляет информацию о удалённых ветках, но ваши файлы и локальные ветки не трогает. После неё git знает, что в origin/main появились изменения (например, влитый PR Ани), но они ещё не у вас в рабочей ветке. Это безопасная команда, сломать ею ничего нельзя.

### `git merge origin/main`

Вливает свежее состояние main с GitHub в вашу текущую ветку feature/boris. Если правки не пересекаются, git сделает всё сам и создаст коммит слияния. Если пересекаются, остановится и напишет CONFLICT, а в файлах расставит маркеры <<<<<<<, =======, >>>>>>>. Вы вручную выбираете, что оставить, потом делаете git add <файл> и git commit, чтобы завершить слияние.

Как избегать таких конфликтов

- Договаривайтесь, кто какие ноутбуки и файлы трогает, и не работайте над одним ноутбуком параллельно.
- Делайте PR небольшими и вливайте их быстро: чем дольше живёт ветка, тем больше расхождение с main.
- Часто подтягивайте main в свою ветку (`git merge origin/main`), чтобы конфликты накапливались по чуть-чуть, а не одним большим куском.

В .ipynb маркеры оказываются внутри JSON, и править их руками рискованно. Используйте nbdime: nbdime mergetool откроет удобный интерфейс слияния. Выводы ячеек из-за nbstripout конфликтовать не будут, поэтому останутся только настоящие расхождения в коде и markdown. Если конфликт запутанный, иногда проще взять версию из main и перенести свои правки заново.

```
pip install nbdime
nbdime config-git --enable --global
```

Эта команда прописывает в глобальный конфиг `git`, что для .ipynb-файлов нужно использовать `nbdime` при `diff` и `merge`. Без `--global` настройка применится только к текущему репозиторию(выбирайте что вам удобнее).

Как пользоваться при конфликте

- Делаете `git merge origin/main` и получаете конфликт в ноутбуке.
- Запускаете:
    ```
    git mergetool
    ```
- Откроется браузер с веб-интерфейсом: слева версия из main, справа ваша, внизу результат. По каждому расхождению выбираете, какой вариант оставить, или правите вручную. Затем жмёте Save и закрываете вкладку.

**Воторой возможный конфликт.** CSV, пересохранённые целиком: если кто-то открыл файл в pandas или Excel и сохранил заново, у него могли измениться порядок строк, форматы чисел, кавычки, разделитель или кодировка. Тогда весь файл выглядит изменённым и конфликтует с любой другой правкой. Сохранять через index=False, не сортировать без необходимости, не править CSV в Excel, а менять данные кодом в ноутбуке.
